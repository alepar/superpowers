## Rejected (with reason)
- §4.1(c) "`--classify` ... runs the `--complete` node block's own section/fence/item state machine ... no second copy" vs "`sub-heading` (... whether or not the section has items yet; it does not open a section, so it and the lines after it keep the enclosing section)" — Rejected 2/3 (reproduce REJECT, refute REJECT, ground CONFIRM at Should-fix). All three seats agree on the mechanism: `--complete` raises the sub-heading error only under `active && hasContent`; an item-less recognized section followed by a deeper heading falls through to closeSection() and opens a new section (report-verdict ~L147-155), so `--complete`'s own transitions would label that line `boundary`, not `sub-heading`. The majority holds that the spec resolves this itself: the role definition explicitly says "whether or not the section has items yet", a specific definition that controls over the general "own state machine" wording; "no second copy" means shared `heading()`/`relevant()`/fence/bullet code, and a classify-mode flag on one heading branch is not a second copy; §4.1(d) leaves `--complete`'s transitions alone, so `--complete` output stays byte-identical as the mlr.21 bead requires; "Section-body grammar errors do not stop classification" already signals that `--classify` need not mirror `--complete` on erroring input. Ground seat's dissent cites the same code and spec text and concedes the mode-flag resolution; it adds nothing the majority does not address, so no escalation. Residual: a wording nit — say that classify mode may differ from `--complete` at item-less sub-headings.
- §4.1(c) rule (iv) checks only per-line `(section, inFence)` and byte identity, not item membership, so prefixing `- ` to a sub-heading or bold label after an open item splits the finding and moves its continuation lines onto a new occurrence — Rejected 2/3 (reproduce CONFIRM at Nit, refute REJECT, ground REJECT). Mechanism agreed by all seats: demoting `### Evidence` to `- Evidence` after `- [Should-fix] a.sh:3 — claim` passes (i)-(iv), and the `verdict:`/`evidence:` lines then belong to the new severity-less item. The majority holds this is the spec's stated behavior: "the repair can only add list markers and `- none`, demote a forbidden sub-heading to an item", a demoted sub-heading is by construction a new item, the existing fixture (tests/super-code/test-report-verdict.sh L558-562, `### detail` → `- detail`) accepts exactly this shape and the spec says such repairs "stay accepted". "Cannot ... move a continuation line" refers to position, order and section, which (iv) checks byte-for-byte; item membership is not a stated guarantee. Finding keys, severities and every line of text are preserved; the original was already a failed parse with exit 4. The proposed fix (forbid the prefix whenever an item is open) would reject the main case the repair exists for (§1, §4.1(d)). Reproduce seat's Nit rests on the same facts and asks only for softer wording, so no escalation. Residual wording nit: soften the closing sentence of (c) to say grouping may change when a sub-heading is demoted. This is the only residue of the iteration-2 "checks (ii)-(iv) blind to continuation lines" finding, which the amended (iv) otherwise resolves.
