# Dossier D2: When do type hierarchies and polymorphism help maintainability, and how should design and review rules adapt across languages?

## Summary

Synthesis. Citations are in the sections below; this summary adds no new source claims.

- **When a hierarchy is meaningful.** The stable criterion is behavioral subtyping. A hierarchy is meaningful when subtype objects preserve everything a client can prove from the supertype's specification: what callers may pass, what they are guaranteed, which exceptions they can meet, and invariants and history. Subclassing mechanics and "is-a" intuitions are not evidence of that. Closed sum-type hierarchies (sealed types) are a second legitimate use; implementation-reuse hierarchies are the contested one.
- **Depth.** Experiments on inheritance depth disagree on direction. The most careful one attributes maintenance effort to the number of methods a maintainer must understand, not to depth.
- **How Java code uses inheritance.** Corpus studies find mostly subtyping. A sizable minority of subclasses rely on late-bound self-calls, which is the precondition for fragile-base-class breakage.
- **Defect classes.** Among hierarchy-specific defect classes, only Refused Parent Bequest (empty-bodied overrides) has causal evidence of harm, from one cohort study on three Java systems. The override rules (no narrowed preconditions, no weakened postconditions, no surprise exceptions) are theory-backed and mechanically checkable but lack defect-rate data. Depth, casts, type switches and speculative abstractions are at most triage cues, or idiomatic in some languages.
- **Languages.** Go, Rust, Python, TypeScript, Haskell and Java/Kotlin with sealed types express polymorphism differently, so review rules must be per-language.
- **F9 slice.** The dispatch-cost evidence is split. One older primary measurement finds a modest median overhead; practitioner microbenchmarks report large gaps on toy problems. Data-oriented design is argued mainly by practitioners.
- **Key uncertainty.** The experiments are old, small and use students. There is one causal smell study. No modern dispatch-cost measurements and no empirical studies of Go or Rust interface practice were found.

### 3. Composition, encapsulation, the fragile base class, and closing extension

- Snyder (OOPSLA '86; primary theory): The introduction of inheritance severely compromises the benefits of encapsulation in most languages, and because the use of inheritance itself is globally visible, changes to the inheritance hierarchy cannot be made safely [30]. <!-- claim: 761b6ca98324cc38; evidence: 350046eb1989f696; source: 0e2c6698c7f2f644 --> The external interface a class provides to its children serves as a contract between the class and its children, and thus limits the degree to which the designer can safely make changes to the class [30]. <!-- claim: 20c737dfd63c5fa0; evidence: a125d74c5fd28d24; source: 0e2c6698c7f2f644 -->
- Liskov's keynote on subclasses that use superclass internals: When encapsulation is violated, we lose the benefits of locality: the combined code of the sub- and superclass must be considered, and reimplementing the superclass may require reimplementing its subclasses too [28]. <!-- claim: 8484edfad42c2eee; evidence: 12f36fa8b817c65b; source: 3049e1862f4ceee5 -->
- Mikhajlov and Sekerinski (ECOOP '98; only the abstract and introduction were read): The fragile base class problem occurs in open object-oriented systems employing code inheritance as an implementation reuse mechanism, where developers unaware of extensions may produce a seemingly acceptable revision of a base class which may damage its extensions [31]. <!-- claim: 0e87e7c48ca9bfe6; evidence: a5032b03c25c8fe5; source: 3f7a73a4e95baa27 --> The vulnerable systems are those employing code inheritance as an implementation reuse mechanism along with self-recursion [31]. <!-- claim: 941ec72b75f4951d; evidence: ecb5007039cbdb6d; source: 3f7a73a4e95baa27 --> However, the paper notes that objects of the extension class can be perfectly substitutable for objects of the base class even if the base class is fragile [31]. <!-- claim: 702f175032dfe7f9; evidence: 36400854493e65de; source: 3f7a73a4e95baa27 -->
- Inference: the corpus studies in §2 find that about a third of Java subclasses rely on late-bound self-reference. That is the self-recursion the fragile-base-class analysis names as the vulnerability, so exposure is common in practice, even though no retrieved study measured breakage rates.
- The composition maxims are known here only secondhand (the GoF and *Effective Java* texts were not read): The corpus paper quotes the instruction of the design-patterns authors to favor object composition over class inheritance [35]. <!-- claim: 2414aee69d03b01d; evidence: d9d0e65a5ddafeaf; source: f8038757c978bb6c --> The same paper reports that Bloch repeats the advice to favor composition over inheritance, based on the argument that this form of inheritance is fundamentally an implementation decision that breaks encapsulation [35]. <!-- claim: b9ec021bee60be21; evidence: 1a99c639e1431ae8; source: f8038757c978bb6c -->
- Prohibiting or closing extension is now a language feature: The sealed-classes proposal aims to allow the author of a class or interface to control which code is responsible for implementing it [51]. <!-- claim: 9db53275ec9db1cc; evidence: 9501b699f2913c69; source: 09a58f4e6f44ed94 --> Java previously assumed that code reuse is always a goal, so a class that can be extended at all can be extended by any number of classes [51]. <!-- claim: 1106fd27799dce69; evidence: e400bdf4db0fc9c5; source: 09a58f4e6f44ed94 --> All direct subclasses of a sealed class are known at compile time, and no other subclasses may appear outside the module and package within which the sealed class is defined [53]. <!-- claim: 79ba68309871286a; evidence: f07f1b63c84b2a20; source: a77ee5767f9781ff -->
- Synthesis: the Java/C# replication in §2 is weak evidence that requiring explicit overridability reduces downcalls (its own causality caveat is anchored there).

### 5. Reviewer-checkable defect classes, by evidence tier

**Tier A: backed by evidence. Refused Parent Bequest (the causal cohort study; primary empirical).**
The cohort study defines Refused Parent Bequest as a class redefining inherited methods using empty bodies, thus breaking polymorphism [38]. <!-- claim: b6ce049b23eb29fb; evidence: 623434dbd16e6f3b; source: a907cdd6b476ebc0 --> Refused Parent Bequest was among the code smells that cause an increase in change-proneness, and the only one also increasing fault-proneness [38]. <!-- claim: d876958315993388; evidence: 51d3e54b6f3f970b; source: a907cdd6b476ebc0 --> The study's overall result is that the presence of code smells appears to be causing a significant increase in change-proneness, while with few exceptions fault-proneness appears unaffected [38]. <!-- claim: 317b15924fe80448; evidence: de647596bf7cbf3f; source: a907cdd6b476ebc0 --> Its limits (three systems, detector precision) are listed under Methodological Limits.

**Tier B: checkable from theory, but no defect-rate data were found.**

- **Overrides that narrow accepted inputs, weaken guarantees, or signal exceptions the supertype does not declare.** Synthesis: the pre-condition, post-condition and exception rules anchored in §1, with the contract-theory rule there, define the test.
- **Overrides that throw "unsupported" errors.** The hazard statement is the Rust Book passage in §4. - **Unguarded downcasts.** Only the paper's abstract was available: The cast study found that casts are widely used, with 8.7% of methods containing at least one cast, and that 50% of inspected casts are not guarded locally against potential run-time errors [39]. <!-- claim: 5b9a1666ce251bc1; evidence: e657dbc2b32fa1a7; source: b017d533998766e5 --> The cast study covers how casting is used by developers in more than seven thousand Java projects [39]. <!-- claim: 3534622f6b536724; evidence: b8394fe9d0ab282d; source: b017d533998766e5 --> The same study identifies 25 cast-usage patterns, recurrent programming idioms using casts to solve a specific issue [39]. <!-- claim: 0fa263825d2e0c76; evidence: 88a1b0b6a25c23d9; source: b017d533998766e5 -->

**Tier C: triage cues only, never blocking findings.**
As a simplistic indicator, a depth of more than three or four seems a good indicator that a hierarchy might warrant closer examination, especially because deeper hierarchies are more likely to add novel methods that cannot be accessed through the root type [37]. <!-- claim: 67dd7e82bb7288e1; evidence: 852ed5d90040d78a; source: 25dd139cd8c47ac8 --> The quality of hierarchies, especially the large problematic ones, may be assessed based on size, shape, and the definition and invocation of novel methods, all properties that can be detected automatically [37]. <!-- claim: f9a32442f17dd48a; evidence: 79b9a9ebf496239a; source: 25dd139cd8c47ac8 --> Inference: the explanation-model results in §2 point to "number of methods a change requires understanding" as a better cue than depth, and together with the size-confounding results in Methodological Limits this argues against treating any depth threshold as a defect.

**Not supported as defect classes by the retrieved evidence.**
The cohort study operationalises Speculative Generality as a class defined as abstract but having very few children that make little use of its methods [38]. <!-- claim: ff865d5902af9afe; evidence: 9365808b5db474ca; source: a907cdd6b476ebc0 --> Whether it was found causal is anchored in Counterevidence item 8. Inference: Go's "no interfaces before use" rule (§4) is a normative guideline, and so is this practitioner advice: A practitioner review guide tells reviewers to be especially vigilant about over-engineering, where developers have made the code more generic than it needs to be [196]. <!-- claim: 338edc1832b4f1f2; evidence: a38ec1900c58e14f; source: b07b3468991ccc7c --> Inference: type inspection in itself is contested (Counterevidence item 4), and the cast-pattern finding above cautions against treating every cast as a defect.

**Primary measurement (Driesen and Hölzle, OOPSLA '96; abstract only).**
The direct-cost study measured virtual-call overhead experimentally for a number of large benchmark programs, using a combination of executable inspection and processor simulation [40]. <!-- claim: 5c35bd389c8c322a; evidence: f283d3a05afaaeec; source: 2d651d2ff24e59e1 --> The C++ programs measured spent a median of 5.2% of their time and 3.7% of their instructions in dispatch code, and the median overhead rose to 13.7% for all-virtuals versions [40]. <!-- claim: f3d2c0aecf52dd98; evidence: 3fd1a656c83f27f4; source: 2d651d2ff24e59e1 -->

**Language documentation.** The Rust Book's dispatch-cost statement and Go's static resolution of methods on concrete types are anchored in §4.

**Practitioner microbenchmark (Muratori, "Clean" Code, Horrible Performance; practitioner).**
The practitioner benchmark reports that replacing the polymorphic version with a switch statement gave an immediate 1.5x performance increase [56]. <!-- claim: f7a96c2016c87c18; evidence: 6028e29519ccbbfe; source: 0d605e60925f672c --> The gap grew from a 10x speed difference to a 15x speed difference after adding one more property to the shapes [56]. <!-- claim: fc6b0f069b4f0f4a; evidence: d03b5ffc6c13f8dc; source: 0d605e60925f672c --> The same author does not consider a switch statement inherently less polymorphic than a vtable, calling them two different implementations of the same thing [56]. <!-- claim: 3ac2c65af59e8669; evidence: 10608f1285419f2c; source: 0d605e60925f672c -->

## Counterevidence and Disagreements

1. **Direction of the depth effect.** The original experiments favoured three levels of inheritance depth, whose subjects performed the maintenance tasks significantly quicker than those maintaining equivalent object-based software [32]. <!-- claim: 5fcd77f702b87140; evidence: 0e5ffef1f6090dc4; source: 18152de2db2dd32e --> The later experiments point the other way: systems without inheritance were easier to modify, and programs with less inheritance were faster to maintain [33, 34]. <!-- claim: 79059e8b42737d86; evidence: 852708a9fb93e069; source: 7ba63c1dfa20668e --> Synthesis: the latest experiment reconciles the conflict by attributing effort to the methods that must be understood (§2). The disagreement is about what depth stands in for, not a settled harm or benefit of depth.
2. **Secondary summaries inverting the primary record.** A secondary summary in the corpus paper states that Daly et al. concluded inheritance had a negative effect on maintenance time and that Cartwright's replication suggested inheritance had a positive effect [35]. <!-- claim: 1ca795cfc57ec9c7; evidence: f8b0d9f32b6a53bd; source: f8038757c978bb6c --> Inference: this is the reverse of Daly's own abstract (§2) and of the experiment paper's account of Cartwright (§2), so secondary characterizations of this literature should not be trusted unchecked.
3. **The composition maxim versus corpus data.** The corpus evidence cuts against strong readings of the composition maxim: there is not huge opportunity to replace inheritance with composition [35]. <!-- claim: b11cd2a00dfa4021; evidence: 0d2e2120517d04c4; source: f8038757c978bb6c --> Cross-reference: the authors' own framing of the composition question is anchored in §2.
4. **Type inspection as a smell.** The abstract-base-class rationale calls the classical OOP view, in which inspection is actively discouraged, simply too dogmatic and inflexible, leading to design rigidity at odds with a language like Python [49]. <!-- claim: 03512426234c7067; evidence: e97db984838cdf92; source: 849a416941265caa --> Synthesis: the sealed-type switch rule (§4) and the practitioner footnote (§6) point the same way, while the unguarded-cast data (§5) point the other way.
5. **How large the dispatch cost is.** The large-benchmark study measured a median of 5.2% of time spent in dispatch code [40]. <!-- claim: b8cc3070b17534c8; evidence: 3fd1a656c83f27f4; source: 2d651d2ff24e59e1 --> However, the practitioner microbenchmark reports a table-driven version that is fully ten times faster or more on the exact same problem [56]. <!-- claim: 0e4c00e508dea994; evidence: 52b59fb8155591c3; source: 0d605e60925f672c --> Synthesis: these numbers come from different regimes (median overhead across large programs versus a toy loop dominated by dispatch and data layout) and cannot be compared directly.
6. **Go return types.** The code-review norm that the implementing package should return concrete types differs from the style-guide advice that the constructor should return an interface value when a type exists only to implement an interface [44, 45]. <!-- claim: 4e1fbc687aae208c; evidence: 38a24b29a72ff162; source: 7d7209181e775e43 -->
7. **Unsupported-operation overrides.** The exception rule of behavioral subtyping sits in tension with a collections design that provides a very small set of core interfaces that can throw a runtime exception [29, 55]. <!-- claim: 5dc52627a448f6be; evidence: 4e86b33f50054b16; source: 171b777c947e90e7 --> Inference: the supertype's documented contract decides whether such an override is a violation.
8. **Speculative abstractions.** The causal evidence singles out Refused Parent Bequest, while Speculative Generality is not among the smells that cause an increase in change-proneness [38]. <!-- claim: a3b2547b56bf247e; evidence: 51d3e54b6f3f970b; source: a907cdd6b476ebc0 -->
9. **More object-oriented design guidance for LLM agents (evidence registered by worker R9 for F11).** A study of LLM-generated projects found that increasing the specificity of OOD guidance tends to produce projects with more classes and higher total complexity, size, and coupling, but lower average values of those metrics [237]. <!-- claim: 4dc1db368ee89861; evidence: 5020c71de7b276f1; source: 19cbec92a90070bf --> Inference: a design-time incentive that rewards adding hierarchies or interfaces may inflate class counts rather than improve substitutability.

## Implications for an agentic design/review workflow

Everything in this section is my inference from the findings above, not a source finding.

- **Design-time incentive.** When an agent introduces an extensible base type or an interface meant for multiple implementations, require a short written supertype contract:
  - what callers may pass and what they are guaranteed;
  - the exceptions callers may see;
  - the invariants and history constraints;
  - the variation subtypes are allowed.

  Without such a contract, the default should be composition, a closed sum type (enum/sealed type with exhaustive matching), or a function parameter. This mirrors the Liskov criteria and avoids rewarding hierarchy creation for its own sake (see the LLM object-oriented design finding).
- **Choose the variation mechanism by the expected axis of change.** Frequent new variants favor open interfaces or traits. Frequent new operations favor closed data types with exhaustive matching. Record the choice in the design.
- **Review findings by tier:**
  - **Tier A (may block, with the contract checked):** empty or throwing overrides of inherited behavior, unless the supertype contract documents the operation as optional.
  - **Tier B (findings with a quoted rule):** overrides that narrow accepted inputs, add undeclared exceptions, or weaken guarantees; match-all `default`/`else` clauses in exhaustive switches over sealed or enum types; unguarded downcasts outside recognized idioms.
  - **Tier C (comments, not findings):** depth beyond three or four, large hierarchies that are mostly reused rather than polymorphic, and changes that require understanding many methods.
- **Per-language adaptation:**

| Language | Flag | Do not flag |
|---|---|---|
| Go | producer-side interfaces created for mocking; interfaces with no consumer yet; misreading embedding as subclassing (no late-bound self) | small consumer-side interfaces; returning an interface when the type has no other exported behavior |
| Rust | trait objects for closed variant sets when an enum would do and dispatch is hot | `dyn` where library users must extend the set |
| Python | ad hoc inspection (checking for methods or concrete base classes) where an ABC or Protocol exists; `isinstance` against non-runtime protocols | `isinstance` against ABCs; Protocols for static duck typing |
| TypeScript | relying on structural compatibility as proof of substitutability; callback-parameter bivariance with `strictFunctionTypes` off | structural typing as such |
| Java/Kotlin | `default`/`else` in exhaustive sealed or enum switches; open hierarchies meant as closed lists of kinds | pattern matching over sealed types; sealed hierarchies with records |
| C++ / hot paths | virtual dispatch in profiled hot loops | virtual dispatch elsewhere |

- **Severity calibration.** Depth thresholds and metric values should never block on their own, given the conflicting experiments and the size confounding of object-oriented metrics.
- **Performance.** Treat dispatch cost as a profiling question. Neither the modest median measurement nor practitioner microbenchmarks justify blanket rules either way.
- **Citation hygiene.** Agents and reviewers that cite "the literature" on inheritance should cite primary sources, since a secondary summary in this facet reverses primary findings.

## Methodological Limits and Open Gaps

The latest depth experiment acknowledges the frequent concern that results from student subjects cannot be generalized to professionals [34]. <!-- claim: e1192b8a185735fb; evidence: 85a5aa180c424aa9; source: a907cdd6b476ebc0 --> The practitioner benchmark says none of its numbers are hard-core measurements, because the differences are so large that no serious analysis tools are needed [56]. <!-- claim: 714da714aa829c8a;
