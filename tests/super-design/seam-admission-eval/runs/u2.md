# Disposition — coverage round 1, `UNOWNED-SEAM · snapshots.csv column layout`

## Disposition

**Applied: ownership fix. No new beads, no seam contract.** The seam admission test fails, so per
§Coverage (Verified `UNOWNED-SEAM`), the layout goes to its one defining task: an `owns:` line on
exp.1 and a `consumes:` line on exp.2, with the open details decided in the spec.

Ledger line:
`cov-1 · r1 · UNOWNED-SEAM · snapshots.csv column layout · applied (ownership) — admission test fails (no class: exp.2 is blocked by exp.1, so not parallel; no volatile dependency; one implementation); exp.1 owns the layout, exp.2 consumes it, layout fixed in spec`

## Reasoning

1. **Verify.** The evidence holds. exp.1's description says it writes `snapshots.csv`, exp.2's
   says it reads that file, and neither `owns:` line names the column layout. exp.1 owns only the
   `stash export` command, and exp.2 consumes only that command. No ledger entry covers this.
   Verified.
2. **Adopt check.** No `Seam contract:` or `Seam integration:` row exists for this boundary, and no
   disposition is replayed. Nothing to adopt.
3. **Admission test (§Decomposition).**
   - **P, parallel boundary: fails.** exp.2 already has a blocking edge on exp.1
     (`blocked-by exp.1: consumes snapshots.csv`). The two tasks never run in parallel, so they
     cannot build the format independently and choose differently. exp.2's implementer reads the
     format exp.1 has already landed.
   - **V, volatile dependency: fails.** The file lives on the filesystem, but R1's check (export,
     then report on the result) is already runnable and deterministic without an abstraction. The
     test can write a CSV to a temp dir and read it back.
   - **N, variation now: fails.** There is one writer, one reader and one format. No requirement
     calls for a second implementation, and no existing call sites branch on a kind.
   - With no class, there is nothing to state an obligation for. The direct check (exp.1 owns the
     layout and exp.2 consumes it, with the layout written in the spec) is enough on its face.
4. **Fix ownership.** The real defect is ambiguity: exp.1 writes the format, but nothing says it
   is exp.1's to define, and nothing pins down the open details (header row, column order, size
   units, quoting). A stated owner plus a spec decision resolves that. Splitting it into a
   contract task would add a task (about five dispatches of ceremony) and an extra round to a
   chain that is already serial, for no parallelism gain.
5. **Edges.** Unchanged. The existing edge exp.2 → exp.1 and its reason line already name the
   consumed artifact. The sweep edge is unchanged too.
6. **Round 2.** This fix changed the tree (two descriptions were amended), so round 2 runs. Its
   `## Changes since the previous round` section names exp.1 and exp.2 with this finding, plus the
   spec diff.

## Spec text to add (root spec, under the R1 design)

```markdown
### snapshots.csv layout

Owned by `stash export` (exp.1); `stash report` (exp.2) consumes it.

- UTF-8 text, RFC 4180 CSV: comma separator, `\n` line endings, fields containing a comma,
  double quote or newline are double-quoted with inner quotes doubled.
- First line is the header, exactly `name,backend,size`. Columns appear in that order.
- One row per snapshot; all snapshots are written. An empty snapshot set produces the header only.
- `name`: the snapshot name as stored. `backend`: the backend identifier as stored, compared
  case-sensitively when grouping. `size`: a non-negative integer number of bytes, no unit suffix.
- `stash report` locates columns by header name, rejects a file whose header lacks any of the
  three columns, and sums `size` per distinct `backend`.
```
