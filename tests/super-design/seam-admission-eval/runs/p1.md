## Graph shape

`.1` → {`.2`, `.3`} (parallel) → `.4`. Longest chain: 3 rounds. `.2` and `.3` both edit
`stash/manifest.py`, `stash/commands.py` and `stash/report.py`, but in separate functions and only
two leaves share them, so no `Split file:` row; the shared registry lines in `__main__.py` were
given to the contract row so neither command task touches that file.

## Seam admission notes

- Admitted: `snapshot-manifests.1`, class P (manifest format and snapshot entry listing exchanged by
  the two parallel command tasks).
- Not admitted: a per-backend snapshot-reader interface (class N candidate: dir and zip). The two
  implementations live inside one `entries()` function, owned by `.2`, matching how `config.py`,
  `report.py` and `commands.py` already branch on backend inline; a reader interface would add a
  layer no requirement checks.
- No class V seam: checks run against temporary directories; no clock, network or subprocess
  dependency needs controlling (`save`'s timestamp only names the snapshot, and tests read the
  name back from `list` or the filesystem).
