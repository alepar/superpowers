# Decomposition: `stash du`, `stash prune`, `stash where` (no-beads mode)

Root spec: `inputs/spec.md` (epic slug `stash-cmds`). The rows below are children of the root, so every row has depth 1.
The root `Integration sweep:` row comes later, after the coverage loop, so it is not listed here.

Decisions made during decomposition:
- **No seam admitted.** Two candidates were checked and both failed the admission test.
  - The default destination `~/.stash/<backend>` is class P only in form. The spec already fixes its value, and it gets one owner (`stash-cmds.1`). The plain way to check it is to assert the same path in all three commands, and that works without any new interface.
  - A backend strategy/registry was considered as class N, since `save`, `list`, `check`, `config.snapshot_suffix` and `report.label` all branch on `dir`/`zip`. The new commands add branches but leave those existing call sites unchanged (save/list/check are out of scope), and only one implementation per backend is needed. Plain `if/elif` branches, tested for both backends, meet R1. The implementer can decide otherwise.
- **Shared helpers have one owner.** The default-destination resolver and the snapshot enumeration that du and prune both need belong to `stash-cmds.1`. du and prune consume them and run in parallel.
- **No file split.** `stash/__main__.py` and `stash/commands.py` are edited by at most two leaves running in parallel (`.2`, `.3`), which is below the 3-leaf split threshold. In `__main__.py` they only append subparsers and dispatch branches. The merge gate absorbs any conflict.
- **Configuration smoke.** R1 × R2 lists configurations (3 commands × {dir, zip} × {`--dest` given, omitted}), so `stash-cmds.4` runs each one. It is a dedicated leaf, not the terminal sweep.
