| stash-tar.1 | 1 | — | Add `tar` backend (save, list, check) with configuration smoke over dir, zip, tar | Register `tar` as a supported backend and implement it in each place that branches on the backend: `config.SUPPORTED` and `config.snapshot_suffix` (`.tar.gz`), `commands.save` (write a gzip-compressed tar of the source tree via `tarfile` mode `w:gz`, members relative to the source), `commands.list_snapshots` (names ending `.tar.gz`), `commands.check` (ok when `zlib`/gzip support is importable), and a new `tar` label inside `report.label` (D1: the label stays in `report.label`, not in a backend). Notes:

- One leaf. The change is roughly a dozen lines across three tightly coupled files that all branch
  on the same backend name; any split lands below the per-bead ceremony floor and would only move
  the coupling into a seam between implementers. With a single leaf there is no sibling boundary,
  so the description carries no `owns:`/`consumes:` lines and the table has no edges.
- Seam admission: none. A backend interface or registry would meet class N's precondition (six
  existing call sites branch on the backend kind: `config.validate` via `SUPPORTED`,
  `config.snapshot_suffix`, `commands.save`, `commands.list_snapshots`, `commands.check`,
  `report.label`). But no obligation can be stated: the direct check (one `tar` branch per call
  site, exercised by the configuration smoke above) catches a missed branch (e.g. a `None` suffix
  or label) and is enough. D1 also pins `report.label` in place, so a backend abstraction could not
  cover all six sites anyway. The planned remote-store backends are a likely future change, which
  is not a seam.
- The configuration smoke (dir, zip, tar) is folded into stash-tar.1 rather than a separate
  `Configuration smoke:` row, because the only leaf can absorb it without becoming a bottleneck.
- The root integration sweep row is created after the coverage loop, which this run skipped.
